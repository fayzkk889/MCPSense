# MCPSense 0.4.1

This patch addresses hostile-description gaps reproduced during fresh end-to-end testing of public0.4.0. The independent npm WebAssembly and native Go installation choices, MIT license and runtime permission controls are preserved.

## Corrections

- Screen privileged retries after denied operations, false success reports despite a processor/operation failure, and invented answers presented as verified facts.
- Screen session-wide integration selection that suppresses alternatives, policy edits removing operator consultation, promotion of quoted/external data into trusted operating instructions, and signing-key disclosure to an output/destination.
- Preserve defensive refusals, public verification material, explicitly fictional generation, actual failure reporting, user-selected current tasks, approval-preserving policy edits and untrusted-data handling. Reporting a completed payment when an optional receipt notification fails and interpreting data for an emulator are separate from the screened trust-boundary crossings.
- Correct an authority-pattern false alarm where mentioning the user after a tool preference was sufficient to imply override.
- Enforce the new user-labelled metadata cases on native and npm CI matrices. Injection results are recorded separately from annotation-consistency review findings; one contradictory test annotation was corrected without changing its description or hostility label.

## Installation

After publication, choose either route:

```sh
npm install -g mcpsense@latest
```

```sh
go install github.com/fayzkk889/MCPSense/cmd/mcpsense@latest
```

npm requires Node.js22+ and includes the Go engine as WebAssembly. Users need no Go compiler, archive utility or MCPSense native executable for that route. Native Go installation requires Go1.22+ without Node.js/npm. Optional native Windows archives remain unsigned and subject to device policy; no route disables protection settings.

## Evidence and limits

The original public0.4.0 onboarding passed all nine command journeys and existing product regressions, but detected only10 of24 hostile metadata observations in the newly labelled sample. The follow-up preserves those failures and adds bounded relational rules and benign counterexamples. Passing the corrected set is regression evidence, not an independent estimate of field accuracy or universal attack prevention. See [the user-test record](user-test-2026-10-25.md) and the exact revision's CI results.

Metadata inspection does not enforce host permissions, isolate sessions, sandbox explicitly authorized MCP processes or inspect all runtime responses. Existing coverage and privacy limitations remain. Detector identity changes with the corrected rules; before/after comparisons require equivalent scanner identity, so generate both reports with the same reviewed version.
